# Asynchronous Polling Helpers

## Status

proposed — pending team alignment on scope, backoff, ergonomics, and terminal-model coverage

This ADR covers acceptance criterion #1 of [#659](https://github.com/SAP/ai-sdk-js-backlog/issues/659) ("investigate and decide on approach"), following the Context Registry release ([#663](https://github.com/SAP/ai-sdk-js-backlog/issues/663)).
No implementation is included; the ticket requires team alignment before code is written.

## Context

Several services expose asynchronous (long-running) operations that return `202 Accepted` and must be polled until they reach a terminal state.
Today a consumer drives the polling loop by hand through `executeRaw()`: read the status location, loop, sleep, and check a terminal condition.
This boilerplate has no timeout, no `Retry-After` handling, and no backoff, and it is rewritten at every call site.

The asynchronous operations in scope were verified against the current specifications.

- `context-registry`: `createUpdateDataDestination`, `createScenarioConfiguration`, and `createTabularArtifact` (`PUT` returning 202).
  Completion is a typed status enum (`PROCESSING`, `ACTIVE`, `ERROR`, `DELETING`), polled on the same resource URL.
- `document-grounding`: `createCollection`, `deleteCollectionById`, `manualTriggerPipeline`, and possibly `createMetadataConfiguration`.
  The terminal models are not uniform (described below).
- `prompt-registry`: no asynchronous operations — every operation is synchronous.

The two services differ structurally.
Both declare a `Location` header on the 202 response.
`context-registry` returns a body with the resource name and completes through a typed status enum on the resource.
`document-grounding` returns no body and completes through field presence in a `oneOf` (`collectionURL` versus `monitorURL`), with an untyped `status` string.
`document-grounding` is also not uniform internally: `deleteCollectionById` terminates on a 404, and `manualTriggerPipeline` has several terminal states plus a partial-success state (`FINISHEDWITHERRORS`).

### Generated client

Clients are generated by `@sap-cloud-sdk/openapi-generator`.
The generator has no custom-template or vendor-extension hooks, so poll support cannot be emitted by the generator itself.
A generic `pollAsyncResource` is already merged in `sample-code/src/utils.ts` and used for the tabular create and delete flows.
That package is private and unpublished, the helper has no exponential backoff and no tests, and it exposes a `sleep` test seam on its public options.

## Decision

Promote `pollAsyncResource` into `@sap-ai-sdk/core` as an internal engine, and expose thin per-service convenience wrappers as the primary consumer surface.
Expose the engine as a pull-model primitive (an async iterator) and layer a thin blocking helper on top that awaits the terminal state and returns `T`; both carry an `AbortSignal` and a `maxWaitTime` budget, and honor `Retry-After` as a wait floor if the service ever emits it.
Defer generator integration, a full poller object, and a runtime strategy enum.
Several points remain open for team alignment and are recorded below; the status stays `proposed` until they are resolved.

## Discussion

### Question 1: Scope — is Prompt Registry included?

**Open — team decision.**
The ticket title says "Prompt & Context Registry", but `prompt-registry` has no asynchronous operations in the current specification.
The effective scope is `context-registry` plus `document-grounding`.
Confirm that Prompt Registry is out of scope, or name the planned future operation this should target.

### Question 2: Standalone helper versus generator integration

**Recommendation: Option A, a standalone helper in the core package.**

#### Option A: Helper in `@sap-ai-sdk/core`

**Pros:** Ships now from the already-merged helper, needs no generator work, and reuses the `node:` imports that core already has in `http-client.ts`.

**Cons:** The helper is not derived from the specification, so each new asynchronous operation is wired up by hand.

#### Option B: Generate poll support from the specification

A build-time `postgenerate` script that reads the specification is feasible, with precedent in `prompt-registry` (which runs orval in `postgenerate`) and in `scripts/update-imports.ts` (which rewrites generated files).

**Pros:** Automatic, easy to find through autocomplete, and scales with the number of endpoints.

**Cons:** Only two services exist today, with divergent completion models; completion predicates cannot be derived from the specification alone; and response headers such as `Location` are not exposed on the generated types.
The abstraction cost exceeds the benefit for now, so this is deferred rather than rejected.

### Question 3: Consumer surface — standalone function, builder method, or per-service wrapper

**Recommendation: the engine in core plus per-service wrappers.**

#### Option A: Standalone function only

Consumers import `pollAsyncResource` and wire `read`, `isComplete`, and `getFailure` themselves.

**Pros:** One generic utility that tree-shakes cleanly.

**Cons:** Every call site repeats the 25-line loop over the 202 response, the `Location` header, and the status check, and it is hard to find.

#### Option B: Method on `OpenApiRequestBuilder`

**Pros:** Easy to find through autocomplete.

**Cons:** The builder is intentionally thin and cannot know which operations are asynchronous, so the method would appear on synchronous operations too, and polling usually calls a different endpoint.
Rejected.

#### Option C: Per-service wrappers over the core engine

Thin wrappers such as `createAndWaitForActive`, `deleteAndWaitGone`, and `runPipelineAndWait`, each owning its terminal model.
This mirrors the hand-written client pattern in `@sap-ai-sdk/foundation-models`.

**Pros:** Removes the per-call-site boilerplate, encapsulates the 404, partial-success, and status-enum differences, and is easy to find.

**Cons:** Hand-written, so each new asynchronous operation needs a small wrapper.

### Question 4: Backoff strategy

**Recommendation: Option A, exponential backoff with jitter.**
Neither specification declares a 429 response or a `Retry-After` header, so the client cannot rely on a server-provided wait hint.
AWS waiters use exponential backoff with jitter for exactly this reason, whereas Azure's long-running-operation library can use a fixed interval because its services do return `Retry-After`.

#### Option A: Exponential backoff with jitter

**Pros:** Matches the ticket text, needs no server hint, and is safe under concurrent bursts of polling.

**Cons:** Slightly more code than a fixed interval.

#### Option B: Fixed interval

**Pros:** Simplest, and a wall-clock `maxWaitTime` is clearer than a maximum attempt count.

**Cons:** Without a server hint it either polls too often or not often enough; a fixed interval is reasonable only once the service emits `Retry-After`.

If the service later emits `Retry-After` (the progress and ETA work may add it), honor it as a wait floor on top of the backoff.

### Question 5: Terminal-model coverage

**Open — team decision.**
Confirm which flows are in scope for the first version: create only, or also `deleteCollectionById` (404 terminal) and `manualTriggerPipeline` (several terminals plus partial success).
This determines whether the engine's completion model must go beyond a binary complete-or-fail, and whether `getFailure` must distinguish partial success from failure.

### Question 6: Return shape — pull-model primitive, blocking helper, or poller object

**Recommendation: a low-level pull-model primitive, with a blocking helper layered on top.**
Expose the core as a pull model (an async iterator the caller advances, yielding each poll result) rather than a loop that runs to completion.
A pull model lets the caller apply its own polling requirements, is a small testable building block, and is the natural foundation for the per-service wrappers from Question 3.
The blocking convenience (await until terminal, returning `T`) is then a thin layer over the primitive, carrying `AbortSignal`, `maxWaitTime`, and progress.

#### Option A: Pull-model primitive plus a thin blocking helper

**Pros:** Low-level and testable; the caller controls cadence and completion; higher-level helpers compose cleanly on top.

**Cons:** Two layers to document instead of one.

#### Option B: Blocking `Promise<T>` only

**Pros:** One call for the common case.

**Cons:** Opinionated and high-level; the caller cannot adjust the loop, and it is harder to test in isolation.

#### Option C: Full poller object with resumable state

**Pros:** Rich control; resumable across processes.

**Cons:** High-level and unnecessary for in-process polling; resumable state is not needed today.

### Service-team inputs needed

- Typical and p99 completion time for asynchronous operations, to set `maxWaitTime` defaults.
- Whether 429 responses with a `Retry-After` header will be emitted at all (its format is already standardised).
- The planned channel and format for the upcoming progress and ETA feature.
- Whether `createMetadataConfiguration` is actually asynchronous, since it has no status endpoint.

The patterns above were derived from the generated clients and the OpenApi specifications, not from the normative North Star guidance, which is internal and was not consulted.
Obtaining it would let us classify canonical versus service-specific behaviour with certainty.
