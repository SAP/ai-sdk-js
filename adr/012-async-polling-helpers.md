# Asynchronous Polling Helpers

## Status

proposed — pending final review (backoff and terminal-model coverage decided; see below)

This ADR covers acceptance criterion #1 of [#659](https://github.com/SAP/ai-sdk-js-backlog/issues/659) ("investigate and decide on approach"), following the Context Registry release ([#663](https://github.com/SAP/ai-sdk-js-backlog/issues/663)).
No implementation is included; the ticket requires team alignment before code is written.

## Context

Several services expose asynchronous (long-running) operations that return `202 Accepted` and must be polled until they reach a terminal state.
Today a consumer drives the polling loop by hand through `executeRaw()`: read the status location, loop, sleep, and check a terminal condition.
This boilerplate has no timeout, no `Retry-After` handling, and no backoff, and it is rewritten at every call site.

The asynchronous operations in scope were verified against the current specifications.

- `context-registry`: `createUpdateDataDestination`, `createScenarioConfiguration`, and `createTabularArtifact` (`PUT` returning 202).
  Completion is a typed status enum (`PROCESSING`, `ACTIVE`, `ERROR`, `DELETING`), polled on the same resource URL.
- `document-grounding`: `createCollection`, `deleteCollectionById`, `manualTriggerPipeline`, and `createMetadataConfiguration`.
  The terminal models are not uniform (described below).

`prompt-registry` is out of scope: it has no asynchronous operations in the current specification.

The two services differ structurally.
Both declare a `Location` header on the 202 response.
`context-registry` returns a body with the resource name and completes through a typed status enum on the resource.
`document-grounding` returns no body and completes through field presence in a `oneOf` (`collectionURL` versus `monitorURL`), with an untyped `status` string.
`document-grounding` is also not uniform internally: deletion is tracked by polling the resource itself — `GET /vector/collections/{id}` returns a 404 once `deleteCollectionById` completes (a typed `/deletionStatus` endpoint returning `Deleted | Pending` also exists) — and `manualTriggerPipeline` has several terminal states plus a partial-success state (`FINISHEDWITHERRORS`).

### Generated client

Clients are generated by `@sap-cloud-sdk/openapi-generator`.
The generator has no custom-template or vendor-extension hooks, so poll support cannot be emitted by the generator itself.
A generic `pollAsyncResource` is already merged in `sample-code/src/utils.ts` and used for the tabular create and delete flows.
That package is private and unpublished, the helper has no exponential backoff and no tests, and it exposes a `sleep` test seam on its public options.

## Decision

Promote `pollAsyncResource` into `@sap-ai-sdk/core` as an internal engine, and expose thin per-service convenience wrappers as the primary consumer surface.
Expose the engine as a pull-model primitive (an async iterator) and layer a thin blocking helper on top that awaits the terminal state and returns `T`.
Both carry an `AbortSignal` and a `maxWaitTime` budget, and back off on 429 using the retry value the service returns in the response body.
Defer generator integration, a full poller object, and a runtime strategy enum.
Several points remain open for team alignment and are recorded below; the status stays `proposed` until they are resolved.

## Discussion

### Question 1: Scope

**Settled.** The scope is `context-registry` plus `document-grounding`.
`prompt-registry` is excluded because it has no asynchronous operations.

### Question 2: Standalone helper versus generator integration

**Recommendation: Option A, a standalone helper in the core package.**

#### Option A: Helper in `@sap-ai-sdk/core`

**Pros:** Ships now from the already-merged helper, needs no generator work, and reuses the `node:` imports that core already has in `http-client.ts`.

**Cons:** The helper is not derived from the specification, so each new asynchronous operation is wired up by hand.

#### Option B: Generate poll support from the specification

A build-time `postgenerate` script that reads the specification is feasible, with precedent in `prompt-registry` (which runs orval in `postgenerate`) and in `scripts/update-imports.ts` (which rewrites generated files).

**Pros:** Automatic, easy to find through autocomplete, and scales with the number of endpoints.

**Cons:** Only two services exist today, with divergent completion models; completion predicates cannot be derived from the specification alone; and response headers such as `Location` are not exposed on the generated types.
The abstraction cost exceeds the benefit for now, so this is deferred rather than rejected.

### Question 3: Consumer surface — standalone function, builder method, or per-service wrapper

**Recommendation: the engine in core plus per-service wrappers.**

#### Option A: Standalone function only

Consumers import `pollAsyncResource` and wire `read`, `isComplete`, and `getFailure` themselves.

**Pros:** One generic utility that tree-shakes cleanly.

**Cons:** Every call site repeats the 25-line loop over the 202 response, the `Location` header, and the status check, and it is hard to find.

#### Option B: Method on `OpenApiRequestBuilder`

**Pros:** Easy to find through autocomplete.

**Cons:** The builder is intentionally thin and cannot know which operations are asynchronous, so the method would appear on synchronous operations too, and polling usually calls a different endpoint.
Rejected.

#### Option C: Per-service wrappers over the core engine

Thin wrappers such as `createAndWaitForActive`, `deleteAndWaitGone`, and `runPipelineAndWait`, each owning its terminal model.
This mirrors the hand-written client pattern in `@sap-ai-sdk/foundation-models`.

**Pros:** Removes the per-call-site boilerplate, encapsulates the 404, partial-success, and status-enum differences, and is easy to find.

**Cons:** Hand-written, so each new asynchronous operation needs a small wrapper.

### Question 4: Backoff strategy

**Decided: exponential backoff with jitter, over a ~60s base interval, plus 429 handling.**
The context-registry team confirmed a READ rate limit of ~1200 requests/minute per endpoint and recommended polling once a minute, so the base interval sits around 60s and never approaches the limit.
The service does return 429 under load, with the retry value in the response body (not a `Retry-After` header); the helper reads that value and backs off when it occurs.
The team agreed to include exponential backoff with jitter as the ticket asks: it is low-effort and sensible even though the rate limit alone would not require it.

Completion times are not yet measured (they depend on the data source and HANA Cloud), but deletion is bounded at ~1 hour, so `maxWaitTime` defaults should be generous (on the order of an hour) and configurable.

### Question 5: Terminal-model coverage

**Decided: cover create, delete, and pipeline in v1, with a single engine.**
The team chose to handle all three flows now rather than ship create-only and split the rest into follow-ups, which would add organisational overhead for little saved effort.
All three fit one model: poll until a terminal state, return the resource, and let the caller interpret the outcome.

- **Create:** the resource reaches `ACTIVE` or `ERROR` (context-registry), or the creation-status union resolves to its created shape (document-grounding).
- **Delete:** effectively binary (gone or not).
  document-grounding exposes a typed `/deletionStatus` endpoint, which is a cleaner signal than the resource's 404.
  context-registry has no delete-status endpoint.
  There, deletion shows as the `DELETING` status and then a 404 once a background job removes the resource, so the `read` needs a 404-to-done guard.
  The 404 handling does not disappear everywhere, but delete stays binary either way.
- **Pipeline:** `manualTriggerPipeline` has several terminals including the partial-success `FINISHEDWITHERRORS`.
  `isComplete` treats every terminal (`FINISHED`, `FINISHEDWITHERRORS`, `TIMEOUT`) as done, `getFailure` fires only on the `*_FAILED` states, and the caller reads `resource.status` to tell success from partial success.

A separate `pollAsyncResourceWithPartialSuccess` engine is not needed: partial success is the caller's interpretation of the returned resource, not a second engine.

### Question 6: Return shape — pull-model primitive, blocking helper, or poller object

**Recommendation: ship the blocking helper as the consumer-facing surface first, built on a pull-model primitive underneath.**
The blocking helper covers the common case in one call; the pull-model primitive is the small, testable building block it is layered on, and can be exposed directly as a follow-up if callers need to drive the loop themselves.
A full poller object is out of scope.

#### Option A: Blocking helper (consumer-facing, first step)

A per-service wrapper hides the involved flow — call the 202 operation and poll the `Location` URL as-is until the union resolves:

```ts
const headers = { 'AI-Resource-Group': resourceGroup };
const raw = await VectorApi.createCollection(body, headers).executeRaw();
// 202 Accepted — raw.headers.location is already the status URL; poll it as-is
// (no need to parse an id back out of it).
const statusUrl = raw.headers.location as string;
const collection = await pollAsyncResource({
  read: () =>
    executeRequest({ url: statusUrl, method: 'get' }, undefined, {
      headers
    }).then(
      r => r.data as CollectionCreatedResponse | CollectionPendingResponse
    ),
  isComplete: r => 'collectionURL' in r, // created-response shape is terminal
  intervalMs: 60_000, // context-registry allows ~1200 reads/min, so 1/min is safe
  maxWaitTime: 60 * 60_000, // operations can run up to ~1h
  signal
});
```

The wrapper is what encapsulates this, so consumers never parse the `Location` or pick an interval themselves.

**Pros:** One call for the common case; hides the `executeRaw`/`Location`/union handling; carries `AbortSignal`, `maxWaitTime`, and backoff internally.

**Cons:** The caller cannot adjust the loop; built on the pull-model primitive (Option B) underneath.

#### Option B: Pull-model primitive (the building block)

The same read, exposed as an iterator the caller advances (proposed shape; the merged helper currently returns a `Promise`):

```ts
for await (const state of pollCollectionCreation(id, headers)) {
  if ('collectionURL' in state) break; // terminal: created
  reportProgress(state); // still pending (CollectionPendingResponse)
}
```

**Pros:** Low-level and testable; the caller controls cadence and completion; the blocking helper and the per-service wrappers compose on top of it.

**Cons:** Two layers to document.

#### Option C: Full poller object with resumable state

```ts
const poller = createPoller(id);
poller.onProgress(cb);
await poller.pollUntilDone();
const state = poller.serialize(); // resume later / in another process
```

**Pros:** Rich control; resumable across processes.

**Cons:** High-level and unnecessary for in-process polling; resumable state is not needed today.

### Service-team inputs

The context-registry (TCR) team answered; the document-grounding (Grounding) team has not yet responded, so its values are assumed by analogy and marked pending.

Context-registry (confirmed):

- READ rate limit ~1200 requests/minute per endpoint; polling once a minute is recommended and safe.
- Completion time is not yet measured (depends on the data source and HANA Cloud); deletion is bounded at ~1 hour, which sets a generous default `maxWaitTime`.
- 429 is returned under load, with the retry value in the response body (not a `Retry-After` header).
- Deletion has no soft-delete state: the resource is removed and a `GET` returns 404 (within ~1 hour); otherwise the `GET` body carries an error message.
- No progress or ETA signal is planned.

Document-grounding (pending): the same questions are out to `#aif-grounding-support`. Structurally its specification mirrors context-registry — no 429 is declared, no progress field exists, and completion uses the creation-status union, the pipeline status enum, or a 404 on delete — so only the operational numbers (rate limit, completion time, 429 body shape) remain to confirm.

`createMetadataConfiguration` is confirmed asynchronous — the specification declares a 202 with a `Location` header ("Document enumeration in progress") — but has no dedicated status endpoint, so completion is tracked by polling the resource at the returned `Location`.

The patterns above were derived from the generated clients and the OpenApi specifications, not from the normative North Star guidance, which is internal and was not consulted.
Obtaining it would let us classify canonical versus service-specific behaviour with certainty.
