# Async Polling Helpers

## Status

proposed — pending team alignment on scope, backoff, ergonomics, and terminal-model coverage

This ADR covers acceptance criterion #1 of [#659](https://github.com/SAP/ai-sdk-js-backlog/issues/659)
("investigate and decide on approach"), following the Context Registry release
([#663](https://github.com/SAP/ai-sdk-js-backlog/issues/663)). No implementation is included;
the ticket requires team alignment before code is written.

## Context

Several services expose asynchronous (long-running) operations that follow the HTTP
`202 Accepted` + poll-until-terminal-state pattern. Today a consumer must drive the polling
loop by hand via `executeRaw()`: read the status location, loop, sleep, and check a terminal
condition. This boilerplate has no timeout, no `Retry-After` handling, and no backoff, and is
rewritten at every call site.

The async operations in scope, verified against the current specs:

- `context-registry`: `createUpdateDataDestination`, `createScenarioConfiguration`,
  `createTabularArtifact` (`PUT` → 202). Completion is a typed status enum
  (`PROCESSING | ACTIVE | ERROR | DELETING`), polled on the **same** resource URL.
- `document-grounding`: `createCollection`, `deleteCollectionById`, `manualTriggerPipeline`,
  and possibly `createMetadataConfiguration`. Terminal models are **not uniform** (below).
- `prompt-registry`: **no async operations** — every operation is synchronous.

The two services differ structurally. Both declare a `Location` header on the 202, but
context-registry returns a body (the resource name) and completes via a typed status enum on
the resource, whereas document-grounding is body-less and completes via field presence in a
`oneOf` (`collectionURL` vs `monitorURL`) with an untyped `status` string. document-grounding
is also non-uniform internally: `deleteCollectionById` terminates on a **404**, and
`manualTriggerPipeline` has multiple terminals plus a partial-success state
(`FINISHEDWITHERRORS`).

### Generated client

Clients are generated by `@sap-cloud-sdk/openapi-generator` (not orval, which only emits zod
schemas for `prompt-registry`). The generator has no custom-template or vendor-extension hooks,
so poll support cannot be emitted by the generator itself. A generic `pollAsyncResource` is
already merged in `sample-code/src/utils.ts` (#2184/#2234) and used for tabular create/delete,
but `sample-code` is private/unpublished, the helper has no exponential backoff/jitter and no
tests, and it exposes a `sleep` test seam on its public options.

## Decision

Promote `pollAsyncResource` into `@sap-ai-sdk/core` as an internal engine, and expose thin
per-service convenience wrappers as the primary consumer surface. Return a `Promise<T>` with an
`onPoll` progress callback, accept an `AbortSignal` and a `maxWaitTime` budget, and honor
`Retry-After` as a wait floor. Defer generator integration, a streaming poller, and a runtime
strategy enum. Several points remain open for team alignment and are recorded below; the status
stays `proposed` until they are resolved.

## Discussion

### Question 1: Scope — is Prompt Registry included?

**Open — team decision.** The ticket title says "Prompt & Context Registry", but
`prompt-registry` has no async operations in the current spec. The effective scope is
context-registry + document-grounding. Confirm Prompt Registry is out of scope, or name the
planned future async operation this should target.

### Question 2: Standalone helper vs generator integration

**Recommendation: Option A (standalone runtime helper).**

#### Option A: Runtime helper in `@sap-ai-sdk/core`

**Pros:** Ships now from the already-merged helper; no generator work; `node:` imports already
exist in core (`http-client.ts`), so no new runtime constraint.

**Cons:** Not derived from the spec, so new async operations are wired up by hand.

#### Option B: Generate poll support from the spec

A build-time `postgenerate` script reading the spec yaml is feasible (precedent: `prompt-registry`
runs `orval` in `postgenerate`; `scripts/update-imports.ts` rewrites generated files).

**Pros:** Automatic, high discoverability, scales with endpoint count.

**Cons:** Only two services with divergent completion models today; completion predicates are not
derivable from the spec alone; response headers (`Location`) are not exposed on generated types.
Abstraction cost exceeds benefit now — deferred, not rejected.

### Question 3: Consumer surface — standalone function, builder method, or per-service wrapper

**Recommendation: engine in core plus per-service wrappers.**

#### Option A: Standalone function only

Consumers import `pollAsyncResource` and wire `read`/`isComplete`/`getFailure` themselves.

**Pros:** One generic utility; tree-shakeable.

**Cons:** Every call site repeats the ~25-line 202/Location/status loop; low discoverability.

#### Option B: Method on `OpenApiRequestBuilder`

**Pros:** Discoverable via autocomplete.

**Cons:** The builder is intentionally thin and cannot know which operations are async, so the
method would appear on synchronous operations too; polling usually calls a different GET endpoint.
Rejected.

#### Option C: Per-service wrappers over the core engine

Thin wrappers such as `createAndWaitForActive`, `deleteAndWaitGone`, `runPipelineAndWait`, each
owning its terminal model. Mirrors the hand-written client pattern in `@sap-ai-sdk/foundation-models`.

**Pros:** Removes the per-call-site boilerplate; encapsulates the 404 / partial-success / status-enum
differences; good discoverability.

**Cons:** Hand-written, so each new async operation needs a small wrapper.

### Question 4: Backoff strategy

**Open — team decision.** The ticket says "add exponential backoff and randomisation", but these
services emit `Retry-After` (so the server already throttles), and Azure's LRO library uses a fixed
interval while honoring `Retry-After`; AWS waiters use exponential backoff + jitter precisely because
Smithy services send no server hint. Decide between:

#### Option A: Literal — exponential backoff + jitter

**Pros:** Matches the ticket text; safe under bursty concurrent polling.

**Cons:** Largely redundant when the server already returns `Retry-After`; jitter only helps
concurrent fan-out, which is not the current usage.

#### Option B: `Retry-After`-driven fixed interval + `maxWaitTime`

**Pros:** Simpler; aligns with the server contract and the Azure precedent; `maxWaitTime`
(wall-clock) is more intuitive than `maxAttempts`.

**Cons:** Deviates from the literal ticket wording — needs the ticket author's agreement.

### Question 5: Terminal-model coverage

**Open — team decision.** Confirm which flows are in scope for the first version: create only, or
also `delete` (404 terminal) and `manualTriggerPipeline` (multiple terminals + partial success).
This determines whether the engine's completion model must go beyond a binary complete/fail and
whether `getFailure` must distinguish partial success from failure.

### Question 6: Return shape — Promise vs poller object

**Recommendation: `Promise<T>` plus an `onPoll` callback.** Cancellation (`AbortSignal`) and
progress (`onPoll`) are already covered; an Azure-style serializable/resumable poller is YAGNI for
in-process polling. The upcoming progress/ETA data will arrive inside the polled resource and flow
through `onPoll`, so a plain Promise does not paint us into a corner.

### Service-team inputs needed

- Typical / p99 completion time for async operations (to set `maxWaitTime` defaults).
- `Retry-After` format on 429 (integer seconds vs HTTP-date).
- Planned channel/format for the upcoming progress/ETA feature.
- Whether `createMetadataConfiguration` is actually asynchronous (it has no `*Status` endpoint).

The patterns above were derived from the generated clients and the OpenAPI specs, not from the
normative North Star async-operations guidance (internal, not consulted); obtaining it would let us
classify canonical vs service-specific behaviour with certainty.
